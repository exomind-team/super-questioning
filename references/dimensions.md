# 六维度详细定义与典型问法

> 本文件为 super-questioning skill 的参考文件，补充 SKILL.md 中六维度的详细定义和典型问法示例。

## D1 — 隐性需求

**原始措辞**：「我没说但实际开发要考虑的」

**定义**：用户没说，但实际开发中一定会遇到的问题。

**典型沉默知识**：错误处理、权限控制、数据迁移、监控可观测性、回滚降级。

**典型问法**：
> 「你提到成功后的流程，但我没听到出错时的处理——错误信息展示、错误日志记录、用户能做什么操作，这三件事你们期望怎么分工？」

---

## D2 — 质量审查

**原始措辞**：「功能层面有待斟酌与完善的」

**定义**：功能已有表达，但细节有待斟酌。

**触发信号**：边界条件不清晰 / 多个等效实现路径 / 优先级不明确。

**典型问法**：
> 「你说『数据要实时』，这里的『实时』是指每秒刷新、毫秒级推送，还是5秒轮询？这三种方案在实现成本和数据量上差异很大。」

---

## D3 — 冗余省略

**原始措辞**：「我表达中有赘余需要省略的」

**定义**：用户表达了但其实不需要的功能或设计。

**识别信号**：同时提多个等效方案 / 用「最好能」「如果可以的话」/ 用复杂机制达成简单目标。

**典型问法**：
> 「你提了方案A和方案B，在当前阶段（没有真实用户反馈），你倾向于先验证哪个？如果方案A能覆盖80%场景，方案B是否值得在这个版本一起做？」

---

## D4 — 缺口填充

**原始措辞**：「需要补充说明以提高计划完整性的」

**定义**：计划中缺少但会导致实现残缺的内容。

**常见缺口**：外部依赖稳定性、数据持久化方案、身份认证、跨设备同步、部署环境。

**典型问法**：
> 「你说数据存在本地，具体指哪里？App沙盒内、用户文档文件夹、还是云端？不同选择决定了数据迁移和备份的方式。」

---

## D5 — 可行性挑战

**原始措辞**：「需要验证必要性与可行性的」

**定义**：需求本身或实现路径存在未知风险。

**高风险场景**：技术栈新无经验、外部依赖不稳定、性能要求超出常规、安全合规、时间极度受限。

**典型问法**：
> 「你提到要对接这个第三方API，它在中国大陆的访问稳定性有实测数据吗？如果它挂了，系统需要降级到哪个状态？」

---

## D6 — 歧义消解

**原始措辞**：「需要具体确认才不会在实现中与用户需求产生差异的」

**定义**：用词模糊，同一件事不同人有不同理解。

**典型歧义词汇表**：

| 模糊词 | 可能的含义 |
|-------|-----------|
| 「优化」| 性能优化 / 代码可读性 / UX |
| 「同步」| 手动拉取 / 定期轮询 / 实时推送 |
| 「用户」| 管理员 / 注册用户 / 匿名访客 |
| 「快速」| < 100ms / < 1s / 感知无延迟 |
| 「备份」| 全量快照 / 增量备份 / 实时双写 |

**典型问法**：
> 「你提到『和服务器同步』，我理解可能是A（手动刷新拉取）、B（每30秒轮询）、C（WebSocket实时推送）三种方式之一。你们目前倾向哪种？」
